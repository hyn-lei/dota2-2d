# 地图内存占用排查与修复

用户反馈 `71d4636` 的画布分辨率回退之后游戏仍卡，并提供真实游戏进程 `18868`、Chrome 任务管理器内存约 553MB。初次检查系统可用内存约 4.5GB，Chrome 显存约 2.2GB / 3GB。前一项修改改善了大画布绘制耗时，地图的原生资源分配仍占用大量内存。

本机 Chrome、DPR 1.5、2560×1340 CSS 视口、i5-6500 和 GTX 1060 3GB。CDP 内存转储在同一地图绘制管线中记录了约 283MiB 原生像素、284MiB GPU 上传缓冲及 283MiB 纹理。JavaScript 堆为几十 MiB，垃圾回收 CPU 采样约占 1–2%。这次样本的主要内存开销来自地图原生资源。

单独绘制实验将原生位图裁剪到镜头区域，原生像素从 283MiB 降到 22MiB，GPU 上传缓冲从 287MiB 降到 27MiB，渲染进程工作集从约 642MiB 降到 121MiB。原始记录为 `artifacts/cropped-map-memory.json`，额外的已解码位图裁剪实验为 `artifacts/cropped-map-memory-crop-decoded.json`。

`src/renderer.js` 现在先准备八分之一尺寸的全图预览，根据实际像素密度与镜头范围加载裁剪位图，范围包含 256 物理像素的移动余量。为了匹配原有 JPEG 分辨率解码，后台解码使用全局 mip 尺寸，提取镜头像素后关闭临时位图。绘制上传的是裁剪结果，缓存保存全图预览、原生镜头区域和一个活动替代区域。初次位图加载失败调用原图解码器，后续区域失败两秒后重试。单个在途任务限制连续移动或缩放期间的并发解码。

镜头跳到已缓存范围之外时，全图预览提供过渡画面，新区域解码完成后恢复目标细节。裁剪像素在 1∶1 读取时与解码原图逐字节一致。缩放时 Skia 对不同绘制区域的双线性舍入略有变化，十二组对照中最大差异为 6 / 255，变化像素低于 1%。测试同时限制单通道最大差异、平均差异和变化像素比例，以验证原图颜色及投影位置。

同一浏览器、种子 42 的游戏测量结果如下，单位为 MiB。采样期间 Canvas 为 3840×2010。

| 场景 | 修复前渲染进程工作集 | 修复后工作集 | 修复前私有内存 | 修复后私有内存 |
| --- | ---: | ---: | ---: | ---: |
| 开局，99 个单位 | 825 | 354 | 467 | 172 |
| 180 秒成熟场景，约 275 个单位 | 861 | 419 | 500 | 215 |

开局约 60 FPS，成熟场景约 59.5 FPS。修复后默认镜头解码位图约 20MiB，成熟固定镜头约 24MiB。游戏 GPU 转储中的上传内存由 284MiB 级降到约 47–79MiB，传输缓存约 41MiB。完整采样记录为 `artifacts/map-memory-before.json`、`artifacts/map-memory-cropped.json` 和对应 `*-trace.json`。

验证覆盖默认镜头内存预算、十二组地图边缘及缩放像素对照、稳定镜头及 Renderer 生命周期复用、缺少 API、同步/异步解码失败、后续裁剪失败后的恢复、4K 成熟对局连续移动、真实鼠标指令及窗口尺寸恢复。五项 `terrain-resolution.test.mjs` 通过。内存回归修改前约 283MiB，因超过 64MiB 断言失败，修改后约 20MiB 通过。后续失败恢复回归在原实现中六秒超时，限频重试后通过。

生产构建版本为 `84091e6d1f46d2f1c09ffc5823fe172b70fd04e526e909c8cc3d603040008a4b`。构建和静态依赖检查通过，编译 69 个 JS 模块、校验 371 个本地引用；生产构建的独立内存回归和裁剪恢复回归均通过。
