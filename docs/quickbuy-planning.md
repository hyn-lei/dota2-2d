# 快速购买材料计划

快速购买的 HUD 和 G 键使用同一份材料计划。英雄离开商店、物品从储藏进入信使 cargo，或者信使暂时死亡时，已经拥有的可用组件不会重新成为待购物品。

## 计划与购买报价

`Inventory.quickbuyPlan(game, hero)` 返回：

```js
{
  targets: [{id, missing, consumed, cost}],
  missing: ['component_id', 'component_id']
}
```

`targets` 保持快速购买队列的顺序。每个目标的 `missing` 是还需购买的叶组件 ID；重复组件保留重复次数。`consumed` 是为该目标预留的真实物品实例，包含储存区、索引和带 UID 的元数据；查询不会消费这些实例。`cost` 是这些缺少叶组件的总价。顶层 `missing` 按目标顺序展开，供 HUD 展示。

组件池来自英雄物品栏、背包、储藏、回城卷轴栏，以及归属该英雄的信使 cargo。组件的 `meta.ownerId` 必须与英雄 ID 相同，并且没有合成锁。死亡信使保留的 cargo 仍属于已购材料。其他英雄的组件、其他英雄信使携带的组件和地上的掉落物不进入该组件池。

全部目标共享实例分配记录：一个圆环只能抵扣一个目标，一个树枝只能抵扣配方中一个树枝位置。配方及替代配方继续使用现有 `recipeParts` 选择最小缺购成本。计划每次根据当前真实物品计算，因此出售、掉落或转移走组件后，其材料需求会恢复；没有永久的“买过就忽略”记录。

根目标代表下一件要购买的物品，不能用已有同名成品抵扣。例如已有护腕后再排护腕，仍会显示第二件所需的完整材料；排两件护腕时，购买一件只移除一项。

`Inventory.purchaseQuote(game, hero, id)` 继续表达当前购买位置能够物理消费的组件和空位，保留普通购买的原有语义。远程直接购买护腕仍只消费储藏中的材料，不会隔空消费随身物品或 cargo。快速购买不能把该报价的 `missing` 直接用作 HUD 的待购计划。

## G 键执行

G 键只处理首个目标。只有物理报价可执行、其缺少叶组件多重集与该目标计划完全一致，而且报价消费的 UID 都属于该目标预留实例时，才直接购买整件目标。

其他情况下只尝试购买计划中真正缺少、当前买得起且可购买的叶组件。如果所有组件已经买齐，但分散储存在英雄和信使等无法立即合成的位置，返回等待运输或合成，不重复付款。回到可合成位置后，已齐材料可以零金币合成。

例如护腕圆环已在信使上、拳套和卷轴在储藏时，计划为空；G 不会再花 155 金币购买一个圆环来替代信使上的圆环。

## 信使完成回传

`Inventory.completeQuickbuyTargets(hero, completedIds)` 按真实完成事件逐项移除最早的对应目标。一个完成 ID 最多移除一个队列项；两个同名完成 ID 可移除两项。它不修改传入的事件数组。

神秘商店购买仍使用现有英雄代理执行 cargo 内的购买和合成。代理的空快速购买队列不影响真实英雄：购买成功并提交金币、cargo 和元数据后，信使入口调用上述 helper，传入本次购买 ID 与实际合成的 `result.completed`。失败购买不回传完成。

完成回传只在这次真实购买时调用。随后运输一个已经合成的成品只转移实例，不再次完成同名目标。例如队列为两件月之碎片，信使买两个振奋宝石合成第一件后，仅保留第二件目标；第一件运到英雄身上后，第二件仍需要两个振奋宝石。

## 验证与边界

回归用例位于 `tests/quickbuy-planning.test.mjs`，使用真实 `Game`、库存和信使运行时，覆盖离店、信使取货、全材料分散等待、重复材料、多个目标共享组件、替代配方、所有权和合成锁、出售和掉落、重复成品目标、信使购买失败、死亡 cargo、普通远程报价以及本地零扣款合成。

按完整用例名执行最小验证，例如：

```powershell
node --test --test-name-pattern='^quickbuy does not repurchase materials collected by the courier$' tests/quickbuy-planning.test.mjs
```

本次修复保留现有物品 ID、7.42 配方数据、库存结构和部署方式，不引入新的存档字段。既有“信使 cargo 满时最终组件被代理报价分配到背包而遭拒绝”的限制不在本次修复范围内。运行时整体边界继续参见 `docs/item-runtime-sources.md`，不把该材料计划称为与 Dota 2 客户端完全等价。
